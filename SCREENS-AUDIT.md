# Аудит экранов — «Безопасная сделка»

**Статус**: снимок на 2026-08-10 (обновлено вторым проходом поверх версии от 2026-08-09), живой документ (обновлять по мере изменения экранов).
**Метод**: для каждого экрана — цель (зачем он существует на этом этапе), задачи (что пользователь должен мочь сделать), критерии приёмки, затем аудит текущей реализации против них. Обновление от 2026-08-10 сверено не только по коду, но и живым прогоном в браузере (Playwright) по всем трём ролям.

---

## Мебельщик

### 1. Список сделок + дашборд (`/furniture-maker`)

**Цель**: мгновенный обзор всех своих сделок и сигнал, что требует внимания прямо сейчас, без захода в каждую сделку по отдельности.

**Задачи**:
- Видеть все сделки одним списком: название, клиент, сумма, статус
- Быстро перейти к созданию новой сделки
- Видеть агрегированную сводку: общий баланс, распределение по этапам, что требует внимания (Epic C10)

**Критерии приёмки**:
- [ ] Список сделок виден сразу, без лишних кликов
- [ ] Дашборд-сводка видна без скролла
- [ ] Клик по сделке из блока «Требует внимания» ведёт прямо на неё

**Аудит**: реализовано полностью (список + дашборд C10). 🟡 **Несогласованность**: список сортируется по алфавиту названия (`localeCompare`), а не по приоритету — у оператора (`OperatorDealsList`) споры явно поднимаются наверх сортировкой, у мебельщика той же логики нет, хотя дашборд уже подсвечивает те же сделки в блоке «Требует внимания». Стоит либо синхронизировать сортировку, либо оставить как есть осознанно (дашборд уже решает эту задачу другим способом).

### 2. Новая сделка (`/furniture-maker/new`)

**Цель**: собрать достаточно данных о заказе для формирования спецификации/КП и договора до показа клиенту.

**Задачи**: ввести название, сумму, контакт клиента, тип мебели, размеры, материал, качество, фурнитуру, срок изготовления.

**Критерии приёмки**:
- [ ] Обязательные поля (название, сумма, телефон клиента) блокируют создание, пока не заполнены
- [ ] Необязательные поля не блокируют
- [ ] После создания — сразу переход на карточку сделки

**Аудит**: реализовано полностью. Мелкий пробел — нет предпросмотра итогового текста договора/КП перед отправкой (мебельщик не видит, как это будет выглядеть для клиента, до реальной отправки) — не критично для пилота. 🟢 **Эталон структуры для приложения**: пронумерованные секции (1–6), иконки типов мебели, явная пометка «Необязательно» — стоит переносить этот паттерн на другие формы (см. находку по форме правок клиента, экран №7). 🟡 Поле телефона (`#contact-phone`) — обычный текстовый инпут без `type="tel"`, на мобильном откроется буквенная клавиатура вместо цифровой.

### 3. Экран сделки (`/furniture-maker/deal/:id`)

**Цель**: единая точка управления конкретной сделкой на любом этапе — понять, что сейчас происходит, что нужно сделать, выполнить действие.

**Задачи**: видеть статус/прогресс, выполнять статус-специфичное действие (отправить/подписать/отметить готово/и т.д.), видеть деньги по сделке, эскалировать при проблеме.

**Критерии приёмки**:
- [ ] На каждом статусе доступно ровно нужное действие, лишнего не показывается
- [ ] Прогресс и текущий шаг понятны без чтения истории статусов
- [ ] Деньги (транши/баланс) видны в контексте сделки

**Аудит**: граф статусов покрыт полностью технически, но это тот самый «набор плашек» — **Epic C9 (систематизация по зонам) не сделан**, намеренно отложен последним. Живым прогоном в браузере (2026-08-10) это подтверждено предметно, не только по коду: и черновик, и согласование показывают 5-8 независимых карточек одного визуального веса подряд, без деления на зоны «статус/заказ/деньги/общение». Оставшийся пробел из раздела 12 PRD — нет прямого «не могу выполнить заказ» кроме эскалации оператору (редактирование черновика и приёмка «с замечаниями» уже реализованы, см. ниже).

🔴 **Новая находка (critical)**: на статусе `completed` блок «Текущий шаг» говорит «Все деньги на счету — доступны к запросу», а пятью строками ниже отдельная зелёная строка утверждает «Сделка завершена, выплаты произведены» — прямое противоречие о том, выплачены деньги или ещё ждут запроса. Тот же класс бага, что чинил `a15e8fd` на баннере/таймлайне, остался в `stepGuidance.ts` для терминального статуса.

🟡 **Новая находка (high)**: `GuaranteeCertificateDialog` авто-открывается сразу после создания черновика и перекрывает весь экран, включая кнопку «Отправить клиенту» — мебельщику приходится закрыть модалку прежде, чем сделать первое осмысленное действие. Стоит заменить на ненавязчивый баннер с кнопкой «Посмотреть сертификат» (она и так уже есть на карточке).

### 4. Верификация «Безопасная сделка» (`/furniture-maker/verification`)

**Цель**: убедить мебельщика в ценности сервиса и собрать данные, формализующие его участие (по решению сессии — не блокирует создание сделок).

**Задачи**: прочитать о преимуществах сервиса, ввести данные юрлица (название/БИН/адрес), задать реквизиты для выплат.

**Критерии приёмки**:
- [ ] После заполнения виден статус «Верифицировано» с датой
- [ ] Форма реквизитов работает прямо здесь, без перехода на другой экран

**Аудит**: реализовано. ✅ **Обновление 2026-08-10**: дубль с экраном «Реквизиты для выплат» устранён — этот экран теперь единственная каноническая точка данных о продавце (юрлицо + реквизиты вместе), отдельный пункт сайдбара для реквизитов убран. 🟡 Поле телефона реквизитов — тот же пробел с `type="tel"`, что и на форме создания сделки (экран №2).

### 5. Реквизиты для выплат (`/furniture-maker/profile`)

**Цель** (изначальная, до появления экрана верификации): отдельная точка редактирования банковских реквизитов.

**Аудит**: ✅ **Устранено (обновление 2026-08-10).** Экран удалён, `FurnitureMakerProfile.tsx` больше не существует как отдельный маршрут — редактирование реквизитов живёт только на экране верификации (экран №4), сайдбар показывает один пункт «Безопасная сделка» вместо двух. Epic A4 закрыт.

## Клиент

### 6. Онбординг (`/client/deal/:id`, статусы `awaiting_client` без телефона)

**Цель**: подтвердить личность клиента и дать первое ощущение доверия (баннер гарантии) до показа условий сделки.

**Задачи**: подтвердить (если контакт уже известен от мебельщика) или ввести имя и телефон.

**Критерии приёмки**:
- [ ] Известный контакт — confirm одной кнопкой без повторного ввода
- [ ] Неизвестный контакт — форма ввода
- [ ] Баннер гарантии виден в обоих случаях

**Аудит**: реализовано полностью, соответствует ТЗ. Пробел — верификация клиента (Epic A3, отложен) шире, чем просто имя/телефон, если относиться к слову «верификация» серьёзно; сейчас это просто контакт без проверки.

### 7. Экран сделки (`/client/deal/:id`, статусы `negotiation` → `completed`)

**Цель**: провести клиента через согласование/оплату/приёмку с постоянным пониманием, что происходит и что от него требуется.

**Задачи**: смотреть условия (кратко и полно), соглашаться/просить правки, подписывать договор и акт, платить, принимать изделие.

**Критерии приёмки**:
- [ ] На каждом статусе — ровно одно ожидаемое действие
- [ ] Прогресс виден визуально, не только текстом
- [ ] Ключевые условия видны без чтения полной спецификации

**Аудит**: реализовано хорошо (прогресс-бар, «Ключевые условия», «Текущий шаг», таймер производства). Из раздела 12 PRD закрыто: правки теперь по всем полям спецификации (не только сумма/срок), приёмка «с замечаниями» реализована. Остаётся: нет пути выйти из сделки до оплаты без формальной эскалации оператору. Живым прогоном подтверждена и здесь проблема «набора плашек» — та же плоская стопка карточек, что и у мебельщика (см. экран №3).

🟡 **Новая находка (high)**: `RevisionRequestForm` — 11 полей-тумблеров (сумма, срок, тип мебели, материал, цвет, качество, фурнитура, 4 размера) одним нерасчленённым списком, без группировки. Контраст с формой создания сделки (экран №2, эталон структуры) в этом же приложении заметен — там те же по сути поля разбиты на 6 пронумерованных секций. Рекомендация: сгруппировать тумблеры по образцу `DealSpecForm` — «Размеры» отдельным блоком, «Материал/цвет/качество/фурнитура» вместе, «Сумма/срок» вместе.

## Оператор

### 8. Список сделок (`/operator`)

**Цель**: обзор всех сделок площадки, споры — на первом месте.

**Задачи**: фильтровать по статусу, быстро находить сделки, требующие вмешательства.

**Критерии приёмки**:
- [ ] Споры визуально выделены и подняты наверх
- [ ] Фильтр по статусу работает

**Аудит**: реализовано полностью, соответствует цели.

---

### 9. Карточка сделки (`/operator/deal/:id`)

**Цель**: разобраться в конкретной ситуации и принять решение (заморозить/инициировать возврат/решить спор/вручную сменить статус).

**Задачи**: видеть полный контекст сделки (характеристики, правки, транши, переписку), управлять спором, вручную менять статус с сохранением инвариантов.

**Критерии приёмки**:
- [ ] `dispute_open`/`cancelled_refunded` недоступны в ручном списке статусов
- [ ] Действия по спору (заморозить/вернуть/решить) соответствуют текущему состоянию

**Аудит**: реализовано полностью. ✅ **Обновление 2026-08-10**: пробел с верификацией закрыт — карточка сделки у оператора теперь показывает баннер «Мебельщик не верифицирован», если верификация не пройдена.

🟡 **Новая находка (medium)**: блок «Вручную изменить статус» (селект + «Применить») — прямой оверрайд графа статусов без диалога подтверждения. Для пилота с одним оператором это может быть осознанным компромиссом скорости, но стоит добавить хотя бы `AlertDialog`-подтверждение (тот же паттерн, что уже используется в `ResetDemoButton`), чтобы случайный клик не переставил статус сделки с реальными деньгами.

### 10. Резерв гарантии (`/operator/guarantee-reserve`)

**Цель**: контроль финансового риска площадки на уровне общего пула, не отдельной сделки.

**Задачи**: видеть лимит/занято/доступно, список сделок, занимающих резерв.

**Критерии приёмки**:
- [ ] Цифры пересчитываются в реальном времени при изменении статусов сделок
- [ ] Список сделок кликабелен

**Аудит**: реализовано полностью, соответствует цели. 🟢 **Новая находка (low)**: подзаголовок страницы — «Первый шаг к формализации резервного фонда (раздел 7 ТЗ)» — это текст для разработчика, утёкший в интерфейс оператора поддержки, который реально видит эту страницу.

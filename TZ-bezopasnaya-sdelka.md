# ТЗ: Пилот «Безопасная сделка» — кликабельный прототип

## 1. Контекст и цель

Asia Mebel запускает пилот модели «Безопасная сделка» — эскроу-сервис между мебельщиком (мастер, изготавливающий мебель на заказ) и клиентом (покупателем). Платформа держит деньги клиента до момента приёмки работы и выплачивает мебельщику траншами, зарабатывая комиссию.

**Гарант сделки на этом этапе — сама компания Asia Mebel, не банк.** Банк-партнёр/номинальный счёт — следующий шаг после пилота (см. раздел 7 «Механизм гарантии» — там же зафиксирован разбор, чего эта гарантия сейчас реально стоит и чем должна быть подкреплена).

Перед разработкой реального бэкенда нужен **кликабельный фронтенд-прототип без бэкенда**, чтобы:
- показать модель сделки реальным мебельщикам и клиентам на демонстрациях;
- проверить, снимает ли эта модель барьер недоверия между сторонами;
- найти узкие места и нестыковки во флоу до того, как в него будут вложены деньги на реальную разработку.

Прототип — не production-код. Цель — максимально реалистично *ощущаться* как работающий продукт, при этом не иметь реального бэкенда, реальных платежей и реальной отправки СМС.

**Формат демонстрации**: один демонстратор показывает флоу, переключая роль через селектор в интерфейсе (Мебельщик / Клиент / Оператор). Реальной синхронизации между устройствами в пилоте нет.

**Технический стек**: React + TypeScript + Vite, Tailwind CSS + shadcn/ui, состояние — React Context + `useReducer` с персистентностью в `localStorage`. Без бэкенда, без реальных интеграций.

## 2. Функциональные требования

### 2.1 Общее
- **Лейаут мебельщика/оператора**: шапка с лого-плейсхолдером (место под будущий бренд Asia Mebel) → отдельная демо-панель под шапкой (role-switcher + «Сбросить демо», визуально помечена как демо-режим) → сайдбар с навигацией (контекстный: у мебельщика «Мои сделки» / «Новая сделка» / «Реквизиты для выплат», у оператора «Все сделки») → футер-плейсхолдер.
- **Лейаут клиента**: тот же принцип шапки и демо-панели, но без сайдбара — mobile-first, клиент открывает по ссылке в мессенджере со смартфона.
- **Кнопка «Сбросить демо»** — возвращает все данные к трём предустановленным сценариям (см. раздел 5), с подтверждением перед сбросом.
- Состояние хранится в `localStorage`, переживает перезагрузку страницы; при несовместимой/повреждённой схеме — откат к сид-сценариям, без падения приложения.
- Везде, где имитируется реальное действие (СМС, оплата, выплата, обращение к оператору), в интерфейсе есть пометка демо-режима.
- **Баннер гарантии** — на ключевых точках недоверия (онбординг клиента, экран оплаты у клиента, экран ожидания оплаты у мебельщика) — явный текст, что Asia Mebel гарантирует клиенту возврат при срыве сделки и мебельщику — получение оплаты при выполнении условий.
- **ErrorBoundary** на верхнем уровне приложения — не даёт странице упасть в белый экран при неожиданной ошибке.
- **Центр уведомлений** — иконка-колокольчик в шапке (у всех трёх ролей), выпадающая панель со списком событий по доступным роли сделкам: текст, статус прочитано/непрочитано, время. Общий компонент для мебельщика/оператора/клиента — работает без сайдбара, поэтому подходит и для mobile-first клиентского лейаута.
- **Блок «Текущий шаг»** — на экране конкретной сделки: заголовок (что происходит сейчас), описание, что требуется от роли зрителя (если требуется), и одно предложение — зачем этот шаг существует. Текст зависит от статуса сделки и роли зрителя (таблица `stepGuidance`, см. раздел 3).

**Вне скоупа пилота** (сознательно не делаем): реальная отправка СМС, реальный платёжный шлюз/банк, реальная API-интеграция с TrustMe.kz (в UI имитируется как внешний сервис подписания — визуальный флоу, без обращения к их реальному API, публичной документации которого нет — см. раздел 8), полностью юридический текст договора/акта (используется развёрнутый текстовый шаблон-плейсхолдер с пометкой, что подлежит юридической доработке), каталог мебели/визуальный конструктор, номинальный/эскроу-счёт (см. раздел 7), push/SMS-уведомления вне приложения (уведомления — только in-app, см. выше).

### 2.2 Мебельщик
- **Список сделок** — карточки: название заказа, бейдж категории мебели (иконка + подпись), имя и телефон клиента (или «Клиент ещё не подключился»), сумма, статус.
- **Создание сделки** — расширенная форма по разделам (все поля кроме названия и суммы опциональны):
  1. Клиент — имя/телефон **для ориентира мебельщика** (отдельно от онбординга клиента по ссылке — если заполнено, используется для пре-заполнения его confirm-экрана, см. 2.3);
  2. Тип мебели — иконки-карточки (Кухня / Спальня / Детская / Гостиная / Прихожая / Мягкая мебель / Офисная / Другое) + отдельный переключатель «Есть мягкие элементы (обивка)»;
  3. Размеры — ширина/высота/глубина, см;
  4. Материал — корпус (ЛДСП/МДФ/Массив/Другое) + цвет/отделка текстом;
  5. Качество — Эконом/Стандарт/Премиум;
  6. Фурнитура — Стандарт/Премиум/Не определено.
  Разбивка платежа (предоплата/финал) и комиссия платформы — фиксированные значения, не редактируются в форме (см. допущение в разделе 3).
- **Гарантия Asia Mebel** — сразу после создания сделки мебельщик видит модальное окно «Сертификат гарантии» (текст сгенерирован из данных сделки: стороны, сумма, условие «100% оплата после подписания акта приёма-передачи обеими сторонами»). Открывается автоматически при первом заходе на карточку новой сделки, повторно — по кнопке на карточке в любой момент. Дата выдачи (`guaranteeIssuedAt`) фиксируется и видна в истории сделки.
- После создания — **генерация уникальной ссылки сделки**, кнопка «Скопировать», и кнопка **«Поделиться»** через `navigator.share()` (нативное меню шаринга на мобильных — WhatsApp и т.д.), показывается только если браузер поддерживает.
- **Экран сделки**: собранные характеристики заказа, референсы от клиента (фото, если загружены), история правок (diff старое→новое).
  - Подписание договора — доступно после того, как клиент нажал «Согласен». Мебельщик проходит имитацию подписания через **TrustMe.kz**: «Открываем TrustMe.kz…» (имитация редиректа) → стилизованный экран на брендинге TrustMe с полным текстом договора (сгенерирован из данных сделки — стороны, предмет, характеристики, цена, разбивка платежа, гарантия платформы, форс-мажор) → ввод кода из СМС (любой код в демо, отправитель в тексте — «TrustMe.kz») → «Возврат в Asia Mebel…» → статус «подписано» приходит как будто от TrustMe. Только после этого клиенту становится доступен его собственный экран подписания.
  - Пока ждём клиента — явное сообщение «Ожидаем подписания от клиента».
  - После оплаты клиентом — «Отметить готово / передать на приёмку».
  - Подписание акта приёма-передачи — тот же паттерн TrustMe.kz-имитации, что и договор: текст акта, мебельщик подписывает **первым**, затем ждём клиента.
  - Кнопка «Позвать оператора / Сообщить о проблеме» — доступна начиная со статуса `negotiation` и на всех статусах после.
- **Реквизиты для выплат** (номер карты + имя держателя) — всплывающая форма в момент, когда первый транш готов к выплате, и постоянная страница в сайдбаре для просмотра/изменения (одни и те же данные). Пока реквизиты не заданы — в блоке «Выплаты» показывается предупреждение вместо суммы на карту; как только заданы — банер «Деньги зачислены на карту •• XXXX — можно закупать материалы», и в списке траншей у каждого — статус выплаты.
- **Мягкая блокировка отправки сделки клиенту** — см. раздел 9: кнопка «Отправить клиенту» заблокирована с объяснением, если не заполнены реквизиты для выплат или исчерпан резерв гарантии платформы.

### 2.3 Клиент
- **Онбординг по ссылке**: если мебельщик уже указал имя/телефон при создании сделки — клиент видит confirm-экран «Это вы? [Имя] · [телефон] — Да, это я» (одна кнопка, без повторного ввода) с возможностью поправить данные. Если контакт не был указан — обычная форма ввода имени/телефона. В обоих случаях — баннер гарантии.
- **Экран сделки**: полные характеристики заказа (тип, размеры, материал, качество, фурнитура — то же, что видит мебельщик, без блока «Контакт»), баннер «Это предварительная оценка, точная стоимость и сроки — после замера» (на статусе `negotiation`).
- **Референсы** — клиент может загрузить фото (Pinterest-референс, фото объекта) — сжимается на клиенте до ~640px перед сохранением, лимит 4 фото на сделку; мебельщик видит их на своей карточке.
- **Согласование**: кнопки «Согласен» / «Запросить правки» (форма правки с явной кнопкой «Отмена», закрывающей форму без отправки).
- **Подписание договора** — доступно после того, как мебельщик подписал первым. Та же имитация TrustMe.kz-флоу (редирект → документ на брендинге TrustMe → СМС-код → возврат), что видел мебельщик.
- **Оплата** — выбор способа: **картой** (форма номер/срок/CVV, мок) или **через банк** (выбор банка из списка → «Перейти в приложение банка», мок). После выбора — статус `payment_processing` с индикацией обработки (текст зависит от способа: у карты — «Обрабатываем платёж», у банка — «Ожидаем подтверждения от банка») и явной демо-кнопкой «Демо: подтвердить оплату» (не автотаймер — управление остаётся у демонстратора). Баннер гарантии — прямо над способом оплаты.
- **Приёмка**: после того, как мебельщик подписал акт первым — клиент проходит ту же имитацию TrustMe.kz и подписывает своей стороной. До этого — просто сообщение ожидания.
- **Эскалация** — кнопка «Позвать оператора / Сообщить о проблеме» доступна начиная со статуса `negotiation`.

### 2.4 Оператор
- **Резерв гарантии** — новый пункт навигации «Резерв гарантии»: лимит / занято / доступно и список сделок, занимающих резерв (см. раздел 9).
- **Список всех сделок** с фильтром по статусу и именем/телефоном клиента в карточке; сделки со спором визуально выделены («требует внимания»), сортируются наверх.
- **Карточка сделки**: характеристики заказа, история правок, транши (со статусом выплаты), переписка, полная история статусов.
- **Действия оператора**:
  - написать сообщение, видимое обеим сторонам;
  - вручную изменить статус сделки — **кроме** `dispute_open` и `cancelled_refunded` (у них своя логика входа: `dispute_open` — только через эскалацию клиента/мебельщика с созданием `DisputeLog`; `cancelled_refunded` — только через «Инициировать возврат» из `dispute_open`; ручной прыжок в обход этого ломает инварианты state-machine — этот баг был найден и закрыт в ревью);
  - **заморозить** — сделка остаётся в `dispute_open`, дальнейшие переходы блокируются, пока оператор не решит спор (обратимое действие);
  - **инициировать возврат** — необратимо переводит сделку в `cancelled_refunded` (мок, без реальных денег);
  - пометить спор решённым (сделка возвращается в статус, из которого был открыт спор).

## 3. Модель данных

- **Deal (Сделка)**: id/slug, мебельщик, контакт от мебельщика (имя/телефон — для ориентира), верифицированный клиент (имя/телефон — после онбординга), название заказа, сумма, % предоплаты/финала/комиссии, тип мебели, мягкие элементы (bool), размеры (Ш×В×Г), материал, отделка, качество, класс фурнитуры, способ оплаты, статус, предыдущий статус (для возврата из спора), флаг заморозки, флаг согласия клиента, история статусов.
- **RevisionEntry (Правка)**: сделка, поле, старое/новое значение, комментарий, время.
- **Transaction (Транш)**: сделка, тип (предоплата/финал), сумма, время выплаты. Статус выплаты (ждёт реквизиты / выплачено) вычисляется на лету по наличию `PayoutRequisites`, не хранится в самой транзакции.
- **DisputeLog (Спор)**: сделка, кто открыл, причина, статус (открыт/решён).
- **Message (Сообщение)**: сделка, автор, текст, время.
- **Attachment (Референс)**: сделка, изображение (base64, сжатое), кто добавил, время.
- **PayoutRequisites (Реквизиты для выплат)**: номер карты, имя держателя, время сохранения — **общие для мебельщика**, не привязаны к конкретной сделке (в пилоте один мебельщик — одна демо-персона).
- **NotificationEvent (Уведомление)**: сделка, роль-получатель (`client`/`furniture_maker`/`operator`), статус сделки на момент события, текст, время, прочитано (bool). Генерируется автоматически на каждый переход статуса — по одной записи на каждую роль, которой это релевантно.
- **Deal.guaranteeIssuedAt** — ISO-время выдачи сертификата гарантии, проставляется автоматически в `createDeal`.
- Новые domain-файлы: `guaranteeTemplate.ts` (генерация текста сертификата гарантии, аналог `contractTemplate.ts`), `stepGuidance.ts` (`Record<DealStatus, Partial<Record<Actor, {title, description, action?, goal}>>>` — источник текста для блока «Текущий шаг» и для `NotificationEvent`).
- **Резерв гарантии** (раздел 9) — вычисляется чистой функцией `calculateGuaranteeReserve(deals): {limit, used, available}` из `Deal[]`, не хранится отдельной сущностью.

**Допущение** (не уточнялось явно с бизнесом): предоплата 50% / финальный платёж 50%, комиссия платформы 10%.

## 4. Граф статусов сделки

```
draft (черновик, мебельщик заполняет условия)
  → awaiting_client (ссылка сгенерирована и отправлена, ждём клиента)
    → negotiation (клиент подключился, смотрит условия)
      → [клиент запрашивает правки] → мебельщик правит → снова negotiation (цикл, N раз)
      → [клиент согласен] → мебельщик подписывает договор (текст + СМС)
        → contract_signing (клиент подписывает договор — текст + СМС)
          → contract_signed
            → payment_pending (клиент выбирает способ оплаты — картой/через банк)
              → payment_processing (обработка платежа — демо-кнопка подтверждения)
                → paid → предоплата авто-выплачивается мебельщику (за вычетом комиссии)
                  → in_production
                    → awaiting_acceptance (мебельщик отметил готово)
                      → мебельщик подписывает акт (текст + СМС)
                        → act_signing (клиент подписывает акт — текст + СМС)
                          → act_signed → финальный транш выплачивается мебельщику
                            → completed
```

**Точки эскалации к оператору** (переход в `dispute_open`, с сохранением статуса, из которого вышли):
из `negotiation`, `contract_signing`, `contract_signed`, `payment_pending`, `payment_processing`, `paid`, `in_production`, `awaiting_acceptance`, `act_signing`.

Из `dispute_open` оператор переводит сделку либо обратно в сохранённый статус (спор решён), либо в терминальный `cancelled_refunded`. Промежуточное состояние «заморожено» — это флаг `frozen` поверх `dispute_open`, не отдельный статус.

## 5. Пользовательские сценарии (демо-данные)

Три предустановленных сценария, доступных после «Сбросить демо» — все доходят до `completed` через полный граф статусов (два подписания СМС на договор, два — на акт, оплата картой):

1. **Happy path** — согласовали без правок → подписали (мебельщик → клиент) → оплатили → выполнили → подписали акт (мебельщик → клиент) → сделка завершена.
2. **Путь с правками** — клиент дважды запрашивает изменение условий, мебельщик правит, история правок видна как diff, затем обычное завершение.
3. **Путь со спором** — сделка доходит до `in_production`, клиент открывает спор («задержка сроков»), подключается оператор, спор помечается решённым, сделка продолжается до `completed`.

## 6. Критерии приёмки

- Все три сценария проходятся кликами от начала до конца без console-ошибок.
- Каждый статус из графа (раздел 4) достижим и визуально отображён (бейдж/цвет).
- Переключение роли не теряет состояние сделки; при переключении роли на карточке конкретной сделки — переход в соответствующую роль по тому же `dealId`, а не на общий список.
- «Сбросить демо» возвращает ровно к трём исходным сценариям.
- Онбординг клиента по ссылке — confirm-экран, если контакт уже известен от мебельщика, иначе форма ввода.
- Интерфейс пригоден для показа на телефоне (клиентский путь, проверено на реальном мобильном вьюпорте) и на ноутбуке (мебельщик, оператор).
- Везде, где имитируются деньги/СМС/обращение к оператору, есть явная демо-пометка.
- Ручное изменение статуса оператором не позволяет обойти инварианты state-machine (`dispute_open`/`cancelled_refunded` недоступны в ручном списке).
- Сертификат гарантии открывается сразу после создания сделки и доступен повторно с карточки сделки в любой момент.
- Оба подписания (договор, акт) проходятся кликами через имитацию TrustMe.kz-флоу без сбоев и без console-ошибок.
- Колокольчик уведомлений показывает актуальный список событий по ролям, с корректным прочитано/непрочитано.
- Блок «Текущий шаг» на экране сделки соответствует текущему статусу и роли зрителя для каждого статуса из графа (раздел 4).
- Кнопка «Отправить клиенту» заблокирована с понятным текстом причины, если реквизиты не заполнены или резерв гарантии исчерпан; разблокируется, когда причина устранена.
- Завершение или отмена сделки корректно освобождает резерв гарантии — видно на странице «Резерв гарантии» у оператора.
- Страница «Резерв гарантии» показывает верные значения лимита, занято и доступно, и список сделок, занимающих резерв.

## 7. Механизм гарантии — разбор (открытый бизнес-вопрос)

При обсуждении баннера «Asia Mebel гарантирует» вскрылась содержательная проблема, которую пилот не решает, но должен держать в виду:

**Момент максимального риска для клиента — это момент, когда у платформы физически нет денег, чтобы его защитить.** Как только клиент платит, предоплата тут же уходит мебельщику (по требованию «чтобы мебельщику упали деньги на закуп материалов» — раздел 2.2). Если после этого мебельщик пропадёт — возврат клиенту идёт не «из его же денег» (их у платформы больше нет), а **из резервных средств компании**. Это меняет смысл гарантии: не «мы подержим твои деньги», а «мы возместим из своего резерва, если мебельщик подведёт».

Точки риска и требуемая реакция:

| Точка | Риск | Под угрозой | Нужное правило |
|---|---|---|---|
| Оплата пришла → предоплата ушла мебельщику | Мебельщик пропал/сорвал сроки | Клиент | Возврат из резервного фонда платформы |
| Изделие передано, акт не подписывается | Клиент тянет / не выходит на связь | Мебельщик | Автовыплата по истечении SLA, если нет обоснованного спора |
| Любой статус, долгая пауза | Непонятно, жива ли сделка | Обе стороны | Таймаут → авто-эскалация оператору (сейчас только вручную) |

**Что не реализовано ни в прототипе, ни как бизнес-правило — требует решения до масштабирования:**
1. **Резервный фонд** — часть комиссии (или отдельный капитал), покрывающая возвраты клиенту после того, как предоплата уже выплачена мебельщику. Без этого гарантия ничем не подкреплена.
2. **Таймауты/SLA** — сейчас эскалация только ручная («Позвать оператора»), нет автоматического «прошло N дней без движения — подключаем оператора сами».
3. **Разделение действий оператора** — «заморозить» (обратимо) и «вернуть» (из резерва, если виноват мебельщик) сейчас не различаются по источнику денег в UI — это нормально для демо, но не для реальной бухгалтерии.
4. **Номинальный/эскроу-счёт** — следующий шаг после пилота: юридически выводит деньги клиента из-под риска банкротства/кассового разрыва компании. Пока не делаем — держим деньги на обычном счёте компании под публичной офертой.

**Уточнение к моменту выдачи гарантии**: сертификат гарантии (раздел 2.2) выдаётся мебельщику сразу при создании сделки — это материализует обещание платформы как этап флоу и даёт трекинг (дата выдачи в истории сделки), но **не решает** вопрос резервного фонда (пункт 1 выше) — гарантия остаётся не подкреплена реальным резервом до отдельного бизнес-решения.

## 8. Открытые вопросы и риски

1. **Точные % предоплаты/финала и комиссии** — допущение (50/50, 10%), нужно подтвердить с бизнесом.
2. **Повторный вход клиента в кабинет** без новой ссылки от мебельщика — решение отложено, определится по ощущениям с демонстраций.
3. **Несколько сделок на одного клиента / несколько мебельщиков** — в пилоте не поддерживается (одна демо-персона мебельщика, один клиент = одна активная сделка).
4. **Механизм гарантии** — см. раздел 7, требует решения бизнеса перед реальной разработкой.
5. **Риск ложного ощущения реальности** — демо-пометки обязательны везде, где имитируются деньги/СМС.
6. **TrustMe.kz — публичного API нет** (проверено на сайте, доступен только маркетинговый лендинг продукта TrustContract: методы ЭЦП/SMS/Face ID/eGov/WhatsApp/Telegram, без документации эндпоинтов) — весь флоу подписания в пилоте является визуальной имитацией внешнего сервиса, не реальной интеграцией. При переходе к реальной разработке потребуется отдельное согласование доступа к API с TrustMe.kz. Отдельный репутационный риск: имитация чужого узнаваемого бренда на демонстрациях должна быть явно помечена как демо-режим, чтобы не создать впечатление реального партнёрства, которого нет.
7. **Бейдж «Гарантия активна» для мебельщика — сознательно отложен.** Это фича будущего маркетплейса (видимый знак отличия продавцов, прошедших онбординг), не пилота с одной демо-персоной мебельщика. Решение принято явно при проработке раздела 9, не забыто.

## 9. Лимит гарантии и мягкая блокировка отправки

Первый конкретный шаг к формализации резервного фонда (раздел 7, пункт 1) — вводится общий пул гарантии на площадку.

- **Лимит гарантии** — константа-плейсхолдер `2 000 000 ₸` (условное значение для пилота, не финальное число бизнеса — может быть изменено позже без пересмотра механики).
- **Занято** — сумма `amount` по сделкам, которые уже отправлены клиенту (`sendToClient` пройден) и находятся не в терминальном статусе (статус не `draft`, не `completed`, не `cancelled_refunded`). Черновики (`draft`) резерв не занимают — гарантия становится «внешней/связывающей» именно в момент отправки клиенту, не в момент создания черновика.
- **Доступно** = лимит − занято.
- **Критерий допуска мебельщика к гарантии** — заполненные реквизиты для выплат (`PayoutRequisites`, уже существующая сущность раздела 3). Отдельной анкеты/онбординг-экрана не вводится — это внутренняя проверка, не видимый пользователю шаг.
- **Мягкая блокировка на кнопке «Отправить клиенту»** — кнопка заблокирована (не скрыта), если:
  - у мебельщика не заполнены реквизиты для выплат — текст: «Прежде чем отправить сделку клиенту, укажите реквизиты для выплат» со ссылкой на страницу реквизитов;
  - ИЛИ сумма сделки не помещается в остаток лимита — текст: «Резерв гарантии исчерпан: не хватает N ₸. Дождитесь освобождения резерва по другим сделкам» (N — точная недостающая сумма).
  - Блокировка снимается сама, без перезагрузки страницы, как только причина устранена (реквизиты заполнены / резерв освободился).
- **Освобождение резерва** — автоматически при переходе сделки в `completed` или `cancelled_refunded`; отдельного события не требуется, «занято» пересчитывается на лету по актуальным данным сделок.
- **Раздел оператора «Резерв гарантии»** (см. 2.4) — новая страница: лимит / занято / доступно и список сделок, занимающих резерв (название, сумма, статус) — детализация того, что входит в «занято».
- **Домен** — новая чистая функция `calculateGuaranteeReserve(deals: Deal[]): { limit: number; used: number; available: number }`. `dealMachine.ts` и `createDeal()` не меняются: `guaranteeIssuedAt` по-прежнему проставляется безусловно при создании сделки (сертификат гарантии как артефакт не зависит от резерва) — гейт лимита применяется отдельно, только на действии отправки клиенту.
- **Бейдж «Гарантия активна» для мебельщика — не делаем в этом пилоте** (см. раздел 8, пункт 7).

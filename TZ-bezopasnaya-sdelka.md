# ТЗ: Пилот «Безопасная сделка» — кликабельный прототип

## 1. Контекст и цель

Asia Mebel запускает пилот модели «Безопасная сделка» — эскроу-сервис между мебельщиком (мастер, изготавливающий мебель на заказ) и клиентом (покупателем). Платформа держит деньги клиента до момента приёмки работы и выплачивает мебельщику траншами, зарабатывая комиссию.

Перед разработкой реального бэкенда нужен **кликабельный фронтенд-прототип без бэкенда**, чтобы:
- показать модель сделки реальным мебельщикам и клиентам на демонстрациях;
- проверить, снимает ли эта модель барьер недоверия между сторонами;
- найти узкие места и нестыковки во флоу до того, как в него будут вложены деньги на реальную разработку.

Прототип — не production-код. Цель — максимально реалистично *ощущаться* как работающий продукт, при этом не иметь реального бэкенда, реальных платежей и реальной отправки СМС.

**Формат демонстрации**: один демонстратор показывает флоу, переключая роль через селектор в интерфейсе (Мебельщик / Клиент / Оператор). Реальной синхронизации между устройствами в пилоте нет.

## 2. Функциональные требования

### 2.1 Общее
- **Role-switcher** — переключатель роли в шапке приложения (Мебельщик / Клиент / Оператор). Переключение мгновенное, не сбрасывает состояние сделок.
- **Кнопка «Сбросить демо»** — возвращает все данные к трём предустановленным сценариям (см. раздел 4).
- Состояние хранится в `localStorage`, переживает перезагрузку страницы.
- Приложение должно нормально открываться на мобильном экране — по легенде клиент открывает ссылку сделки в мессенджере со смартфона.
- Везде, где имитируется реальное действие (СМС, оплата, выплата), в интерфейсе есть пометка, что это демо-режим — чтобы у реальных участников демонстрации не создавалось ложное ощущение, что прошла настоящая транзакция.

**Вне скоупа пилота** (сознательно не делаем): реальная отправка СМС, реальный платёжный шлюз, юридически полный текст договора (вместо этого — карточка с ключевыми условиями), каталог мебели/конструктор товара.

### 2.2 Мебельщик
- **Список сделок** — карточки с товаром, клиентом (если уже подключился), суммой и статусом.
- **Создание сделки** — форма: имя клиента (для ориентира, телефон подтянется позже), описание товара, сумма, сроки изготовления. Разбивка платежа (предоплата/финал) и комиссия платформы — фиксированные значения, не редактируются в форме (см. допущение в разделе 3).
- После создания — **генерация уникальной ссылки сделки** и кнопка «Скопировать ссылку», которую мебельщик отправляет клиенту сам, вне системы (мессенджер).
- **Экран сделки**: условия, история правок клиента (diff старое→новое), кнопка «Подписать» — доступна после того, как клиент нажал «Согласен», и должна быть нажата мебельщиком **первой**, фиксируя финальные условия; только после этого клиенту открывается экран ввода СМС-кода. Далее — статус оплаты и траншей, кнопка «Отметить готово / передать на приёмку», кнопка «Позвать оператора / Сообщить о проблеме» (доступна с момента `negotiation`), просмотр переписки с оператором при споре.

### 2.3 Клиент
- **Онбординг по ссылке**: первый переход по ссылке сделки → экран с приглашением от мебельщика → ввод номера телефона (без кода подтверждения) → создаётся кабинет клиента (мок), привязанный к этой сделке.
- **Повторный вход в кабинет** — на первую версию: через ту же ссылку сделки (см. открытый вопрос 6.2 — решение примем по ощущениям с демонстраций).
- **Экран сделки**: условия, кнопки «Согласен» / «Запросить правки» (форма правки с комментарием), история правок.
- **Подписание договора** — экран ввода СМС-кода (демо: подходит любой код).
- **Оплата** — экран «Оплатить 100%» (мок, без реального ввода карты).
- **Отслеживание** — статус производства.
- **Приёмка** — кнопка «Принять работу / подписать акт».
- **Эскалация** — кнопка «Позвать оператора / Сообщить о проблеме» доступна начиная со статуса `negotiation` (как только клиент подключился) и на всех статусах после — открывает спор и подключает оператора. У мебельщика на экране сделки есть аналогичная кнопка, доступная с того же момента (например, клиент не выходит на связь при согласовании).

### 2.4 Оператор
- **Список всех сделок** с фильтром по статусу; сделки со спором визуально выделены («требует внимания»).
- **Карточка сделки**: полная история (условия, правки, чат, транши, статусы).
- **Действия оператора**:
  - написать сообщение, видимое обеим сторонам;
  - вручную изменить статус сделки;
  - **заморозить** — сделка остаётся в `dispute_open`, дальнейшие переходы статуса блокируются, пока оператор не решит спор (обратимое действие);
  - **инициировать возврат** — необратимо переводит сделку в терминальный статус `cancelled_refunded` (мок, без реальных денег);
  - пометить спор решённым (сделка возвращается в статус, из которого был открыт спор).

## 3. Модель данных и статусная модель

### 3.1 Сущности
- **Deal (Сделка)**: id, ссылка/slug, мебельщик, клиент (телефон, появляется после онбординга), товар, сумма, % предоплаты, % финального платежа, % комиссии платформы, статус, таймстемпы смены статусов.
- **RevisionEntry (Правка)**: сделка, автор (клиент), поле, старое значение, новое значение, комментарий, время.
- **Transaction (Транш)**: сделка, тип (предоплата / финал), сумма, статус (ожидает / выплачен), время выплаты.
- **DisputeLog (Спор)**: сделка, кто открыл, причина, сообщения оператора, статус (открыт / решён).
- **Message (Сообщение)**: сделка, автор (клиент / мебельщик / оператор), текст, время.

**Допущение** (не уточнялось явно, для пилота фиксируем и помечаем как открытый вопрос к бизнесу): предоплата 50% / финальный платёж 50%, комиссия платформы 10%.

### 3.2 Граф статусов сделки

```
draft (черновик, мебельщик заполняет условия)
  → awaiting_client (ссылка сгенерирована и отправлена, ждём клиента)
    → negotiation (клиент подключился, смотрит условия)
      → [клиент запрашивает правки] → мебельщик правит → снова negotiation (цикл, N раз)
      → [клиент согласен] → мебельщик нажимает «Подписать» (фиксирует финальные условия)
        → contract_signing (ввод СМС-кода клиентом)
          → contract_signed
            → payment_pending (ждём оплату 100% от клиента)
              → paid → предоплата авто-выплачивается мебельщику (мок, за вычетом комиссии)
                → in_production
                  → awaiting_acceptance (мебельщик отметил готово)
                    → act_signed (клиент подписал акт) → финальный транш выплачивается мебельщику
                      → completed
```

**Точки эскалации к оператору** (переход в `dispute_open`, с сохранением статуса, из которого вышли, чтобы вернуться):
- из `negotiation` — если правки идут по кругу и стороны не могут договориться;
- из `in_production` / `awaiting_acceptance` — если клиент недоволен сроками или качеством.

Из `dispute_open` оператор переводит сделку либо обратно в сохранённый статус (спор решён), либо в терминальный `cancelled_refunded`.

## 4. Пользовательские сценарии (демо-данные)

Три предустановленных сценария, доступных после «Сбросить демо»:

1. **Happy path** — согласовали без правок → подписали → оплатили → выполнили → приняли по акту → сделка завершена.
2. **Путь с правками** — клиент дважды запрашивает изменение условий (например, сумму и срок), мебельщик правит, история правок видна как diff, затем обычное завершение.
3. **Путь со спором** — сделка доходит до `in_production`, клиент открывает спор («задержка сроков»), подключается оператор, пишет обеим сторонам, спор помечается решённым, сделка продолжается до `completed`.

## 5. Критерии приёмки

- Все три сценария проходятся кликами от начала до конца без console-ошибок.
- Каждый статус из графа (раздел 3.2) достижим и визуально отображён (бейдж/цвет).
- Переключение роли не теряет и не путает состояние текущей сделки.
- «Сбросить демо» возвращает ровно к трём исходным сценариям.
- Онбординг клиента по ссылке работает как отдельный первый экран (до попадания в общий экран сделки).
- Интерфейс пригоден для показа на телефоне (клиентский путь) и на ноутбуке (мебельщик, оператор).
- Везде, где имитируются деньги/СМС, есть явная демо-пометка.

## 6. Открытые вопросы и риски

1. **Точные % предоплаты/финала и комиссии** — сейчас зафиксированы как допущение (50/50, 10%), нужно подтвердить с бизнесом до реальной разработки.
2. **Повторный вход клиента в кабинет** без новой ссылки от мебельщика — решение сознательно отложено, определится по ощущениям на первых демонстрациях (возможные варианты: только по ссылке, либо отдельный вход по номеру телефона).
3. **Несколько сделок на одного клиента** — в пилоте не поддерживается (один клиент = одна активная сделка), актуально для расширения после пилота.
4. **Риск ложного ощущения реальности** — демо-пометки на СМС/оплате обязательны, чтобы участники демонстрации не решили, что деньги реально списались.
5. **Долгое ожидание оплаты клиентом** — таймауты и напоминания не в скоупе пилота, отслеживается только статусом.

# Безопасная сделка

Платформа сделок с защищённым платежом между заказчиками мебели и производителями.
Пилот: 3–5 производителей, Алматы, ручное сопровождение сделок менеджером.

## Документы

Читай перед работой над задачей, не пересказывай в коде:

- `docs/PRD-safe-deal.md` — требования, машина состояний, критерии приёмки. Источник истины. Версия указана внутри документа.
- `docs/design-spec.md` — токены, компоненты, тексты интерфейса.
- `docs/reference/status-page.html` — визуальный референс. **Не исходник**, верстать заново по спеке.
- `docs/AUDIT-prototype-vs-prd.md` — сверка прототипа с PRD: что приведено в соответствие, что осознанно не тащим в демо, что ждёт решения PM.
- `docs/HANDOVER.md` — состояние работы, принятые решения, открытые вопросы. **Читать первым в новой сессии.**

При расхождении PRD и кода прав PRD. При расхождении PRD и дизайн-спеки — спроси, не выбирай сам.

## Что это за репозиторий

**Кликабельный прототип для демонстраций, не боевой продукт.** Бэкенда нет, состояние живёт
в `localStorage`, деньги, SMS и подписание имитируются. Прототипом закрывается блокер №1 из
плана релиза PRD — набор мебельщиков; боевая разработка стартует, когда они согласятся.

Отсюда правило: требования PRD делятся на три корзины — что видит участник демонстрации
(приводим в соответствие), невидимая инфраструктура надёжности (не тащим), пограничное
(решает PM). Разбор по каждому пункту — в `docs/AUDIT-prototype-vs-prd.md`.

## Стек

- React 18 + TypeScript, сборка Vite
- Tailwind CSS + shadcn/ui (Radix), иконки lucide-react
- Состояние: React Context + `useReducer`, персистентность в `localStorage`
- Тесты: vitest (только domain-слой, компонентных тестов нет)
- Бэкенда, базы данных и платёжного провайдера нет и не планируется в контуре прототипа

## Команды

```bash
npm install
npm run dev
npm test
npx tsc -b
```

Линтера в проекте нет — роль проверки выполняют `npx tsc -b` и `npm test`. Прогоняй оба перед
тем, как считать задачу сделанной, плюс сквозной прогон в браузере: тесты покрывают domain,
но не то, что видит человек на экране.

Каждый рабочий каталог в `.claude/worktrees/` — это ещё одна копия тестов, и `npm test`
прогоняет их все. Прогоняй `npx vitest run --dir src`: он смотрит только на основное дерево.
Ворктри после слияния удаляй — `git worktree remove <путь>`.

## Структура

```
src/
  domain/      чистая логика и тесты: машина состояний, деньги, лимиты, окно приёмки, шаблоны документов
  store/       DemoProvider — reducer, экшены, валидация сохранённого состояния
  pages/       экраны по ролям: FurnitureMaker*, Operator*, ClientDealEntry
  components/  переиспользуемые блоки; components/ui — примитивы shadcn
  layouts/     каркасы для кабинета и клиентского пути
docs/          PRD, дизайн-спека, аудит, визуальный референс
```

Бизнес-правила живут в `src/domain/` и покрыты тестами. Логику, двигающую деньги или статусы,
добавляй туда, а не в компоненты: гейты в UI допустимы как подсказка, но не как единственная
защита.

## Конвенции

- Язык интерфейса — русский. Строки не хардкодятся в компонентах, выносятся отдельно: казахская версия вероятна.
- Деньги в прототипе — целые тенге. Требование PRD хранить в тиынах относится к боевому продукту; здесь оно не выполняется сознательно, см. корзину «не тащим в прототип» в аудите.
- Суммы выводятся компонентом `Money`, а не вызовом `formatMoney` в JSX: дизайн-спека требует моноширинные табличные цифры и называет сумму основным шрифтом ошибкой. Внутри связного предложения — обычный текст.
- Даты: `formatDate` для интерфейса (год опускается, если текущий), `formatDocumentDate` для договора, акта и сертификата — документ обязан нести год.
- Имена состояний сделки в коде совпадают с именами из PRD дословно.
- Комментарий объясняет, **почему** так, а не что делает строка. Особенно там, где решение выглядит странным без контекста PRD.

## Чего не делать без вопроса

- Не добавляй переходы между состояниями, которых нет в PRD.
- Не меняй суммы, доли траншей и сроки таймаутов — они продуктовые решения, не технические.
- Не добавляй пятый исход спора и не делай «устранение недостатков» доступным вне окна приёмки: набор из четырёх исходов закрыт FR-26. Сроки разбора и эскалации в код не входят — они в регламенте оператора.
- Не добавляй в интерфейс элементы из списка запретов в разделе 2 дизайн-спеки.
- Не выбирай библиотеку для платежей, авторизации или уведомлений самостоятельно — предложи варианты.
- Не пиши тесты, подогнанные под текущую реализацию. Тест проверяет критерий приёмки из PRD.

## Как работать экономно

Правила выведены из практики: они срезают расход, не пропуская ошибки. Всё, что ловилось за
прошлые сессии, ловилось тестами, `/review` и проверкой «есть ли обещанное действие» — эти
три вещи не сокращаются.

- **Правки — через Edit.** Изменение файла из `sed` или `node -e` заставляет харнесс вернуть
  весь файл в контекст: сотни строк за одну правку в две строки. Скрипт оправдан только для
  механической замены в пяти файлах сразу.
- **Браузер отвечает на четыре вопроса:** рендерится ли, чиста ли консоль, есть ли на экране
  действие, которое обещает текст, и как это выглядит. Арифметику и правила переходов
  проверяют тесты — дублировать их кликами не нужно.
- **Состояние читать одним вызовом**, возвращающим JSON со всеми нужными фактами, а не пятью
  подряд.
- **`get_page_text` для текста, скриншот — для внешнего вида.** Скриншот ради проверки
  формулировки дороже в разы.
- **Не перечитывать файл после успешного Edit** — правка либо применилась, либо вернула ошибку.
- **`/review` — после логически завершённого куска**, а не после каждой функции внутри него.

## Особое внимание

Деньги и необратимые действия. Любая операция, двигающая средства, обязана быть идемпотентной и логироваться. Если видишь место, где повторный запрос приведёт к двойному списанию или двойному переводу, — останавливайся и сообщай, даже если задача была про другое.

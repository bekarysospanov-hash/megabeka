# design-sync: заметки по этому репозиторию

Репозиторий — **не библиотека дизайн-системы, а приложение-прототип** (Vite + React + TS,
Tailwind + shadcn/ui). Ни Storybook, ни library-сборки, ни `dist`. Всё ниже — следствия
этого факта; без них следующая синхронизация переоткрывает те же грабли.

## Устройство сборки

- `shape: "package"`, синтезированный entry. **`srcDir` сужен до `src/components`** — это
  не косметика: при `srcDir: "src"` в синтезированный entry попадает `src/main.tsx`, который
  на верхнем уровне модуля вызывает `createRoot(document.getElementById('root')!)`. Бандл
  падает целиком (`window.AsiaMebelDS` пустой, `[BUNDLE_EXPORT] 77/77 not a component`), то
  есть сломался бы **любой** дизайн, загрузивший `_ds_bundle.js`. Заодно из entry уходят
  страницы, лейауты и `App.tsx`.
- `cfg.buildCmd` = `node .design-sync/build-types.mjs`. Скрипт делает три вещи:
  1. `tsc --emitDeclarationOnly` (конфиг `.design-sync/tsconfig.types.json`) → `ds-types/`;
  2. barrel `index.d.ts` в корне репозитория + runtime-barrel `ds-types/ds-entry.ts`;
  3. пересборку `.design-sync/tailwind.built.css` (`cfg.cssEntry`).
- Конвертер вызывается с `--entry ./ds-types/ds-entry.ts`. **Без `--entry` он ищет пакет в
  `node_modules/<pkg>`, которого в собственном репо нет.** Симлинк `node_modules/<pkg> → .`
  как решение НЕ подходит: `findTypesRoot` возвращает корень пакета, ts-morph начинает
  обходить `<pkg>/node_modules/<pkg>/node_modules/…` и падает с `ENAMETOOLONG`.
- **Зачем barrel `index.d.ts` в корне.** `lib/dts.mjs` берёт entry дерева типов как
  `<pkgDir>/index.d.ts`, когда в `package.json` нет поля `types`. `package.json` намеренно
  не трогаем (это приложение, поле `types` там смысла не несёт), поэтому barrel
  генерируется в корень и лежит в `.gitignore`. Без него все 77 контрактов выродились бы в
  `{ [key: string]: unknown }` — дизайн-агент не увидел бы ни `variant` у Button, ни
  `status` у StatusBadge.

## Контракты `.d.ts`

- `cfg.dtsPropsFor` закрывает три класса промахов экстрактора — не удаляйте записи, не
  проверив, что автоматика справилась сама:
  1. **`DealStatus` схлопывается в `unknown`.** Union из 16 строковых литералов длиннее
     240 символов, а `lib/dts.mjs` (`emitBody`) на этом пороге отдаёт `unknown`. Затронуты
     `DealProgressBar`, `StatusBadge`, `StepGuidanceCard` — union прописан вручную.
     **При изменении графа статусов в `src/domain/types.ts` эти три записи надо обновить.**
  2. **Компоненты без пропсов** получали `[key: string]: unknown`, то есть «можно что
     угодно» — прямая дезинформация. 11 компонентов описаны явно.
  3. **`Input` / `Textarea`.** Их пропсы — это целиком `React.InputHTMLAttributes` /
     `TextareaHTMLAttributes`, а конвертер намеренно фильтрует React-пропсы, и не остаётся
     ничего, кроме `className`. Полезное подмножество (type, placeholder, value, onChange,
     disabled, rows …) прописано вручную.
  4. **`ToggleChips`** дженерик (`<T extends string>`), и экстрактор выдавал `options: T[]`
     с несвязанным `T` — невалидный TS. Заменено на конкретный `string`.
- **Известное ограничение (не исправлено).** Пропсы, типизированные доменными
  интерфейсами, эмитятся как висячие имена: `deal: Deal`, `transactions: Transaction[]`,
  `messages: Message[]` — без `import`. `[DTS_PARSE]` это пропускает, но сами по себе имена
  для дизайн-агента ничего не значат. Поэтому доменная модель описана в
  `.design-sync/conventions.md`, который целиком уезжает в README и попадает агенту в
  системный промпт. **Если правите conventions.md — держите доменную модель в нём
  синхронной с `src/domain/types.ts`.**

## Превью

- `cfg.provider` = `PreviewShell` (`.design-sync/preview-shell.tsx`, попадает в бандл через
  runtime-barrel). Это `<MemoryRouter initialEntries={['/furniture-maker']}><DemoProvider>`.
  Нужны оба: доменные компоненты читают состояние сделок из `DemoProvider`, а
  `Sidebar`/`BackLink`/`NotificationBell` — маршрут. `MemoryRouter`, а не `BrowserRouter`:
  карточка живёт в iframe без истории. Начальный маршрут задаёт роль «мебельщик», поэтому
  вариант оператора у роль-зависимых компонентов статично не показать.
- **Фикстуры — литералы, не домен.** `.design-sync/fixtures.ts` собран руками, хотя в репо
  есть `src/domain/seedScenarios.ts`. Причина: домен генерирует id через `generateId()` и
  метки времени через `new Date()`, поэтому скриншоты и оценки «плыли» бы на каждой сборке
  без единой правки кода. **В превью запрещены `new Date()`, `Date.now()`, `Math.random()`.**
- **⚠️ ГЛАВНОЕ ПРО ДАТЫ: часы в capture заморожены на 2024-05-15, а фикстуры датированы 2026.**
  `package-capture.mjs:102` делает `page.clock.setFixedTime(new Date('2024-05-15T12:00:00Z'))` —
  это НЕ баг и не «отстающие часы» (чистый chromium показывает системное время), а намеренная
  фиксация ради детерминизма скриншотов. Но `.design-sync/fixtures.ts` живёт в 2026 году,
  поэтому любой компонент с арифметикой «сейчас минус дата из фикстуры» считает разницу в два
  года: `ProductionTimer` печатал «Осталось 840 дн.», а ветка «просрочено» была недостижима
  в принципе. Обход в превью `ProductionTimer` — даты старта производства заданы 2024 годом;
  он корректен и детерминирован (часы стоят, счётчик не ползёт).
  **Правильное лечение на будущее:** привести эпоху фикстур к эпохе харнесса — либо пересчитать
  даты в `fixtures.ts` относительно 2024-05-15, либо вынести `NOW` в фикстурах в одну константу
  и синхронизировать её с `setFixedTime`. Не сделано в этот заход сознательно: правка фикстур
  сбрасывает оценки всех превью, которые их импортируют, и требует полного переснятия.
  **Проверять при каждой ресинхронизации:** если capture-скрипт сменит эпоху, все превью
  с датами надо пересмотреть.
  **Важное уточнение области действия правила** (проверено в батче коммуникации): оно касается
  ТОЛЬКО компонентов, считающих «сейчас минус дата». Компоненты с абсолютной меткой —
  `MessageThread` печатает `formatDateTime` = `Intl.DateTimeFormat('ru-RU')`, то есть ровно то,
  что лежит в пропсе, — должны оставаться в эпохе фикстур (2026). Перевод их на 2024 поставил бы
  переписку на два года раньше статусной истории сделки. Из всех 77 компонентов относительное
  время считает только `ProductionTimer`.
- **Шим `'asia-mebel-bezopasnaya-sdelka'` НЕ проверяет экспорты.** Импорт несуществующего имени
  собирается без единой ошибки, а на карточке даёт пустой кадр — то есть ловится только глазами
  по скриншоту. Реальный случай: `LinkCopyBox` («скопировать ссылку клиенту») объявлен локально
  внутри `src/pages/FurnitureMakerDealDetail.tsx`, компонентом ДС не является, но превью с его
  импортом собралось. Если такой блок нужен в дизайн-системе — выносить в `src/components/`.
- **`generateContractText` / `generateActText` нельзя звать из превью** — обе подставляют
  `new Date()`. Текст документа в превью задан литералом по тому же шаблону.
- **`formatMoney` печатает «360 000 KZT», а не «360 000 ₸» — ВЕЗДЕ, а не только в карточках.**
  Первая версия этой записи (со слов агента) винила headless-браузер. Это неверно, проверено:
  `new Intl.NumberFormat('ru-RU', {style:'currency', currency:'KZT'})` даёт «216 000 KZT»
  и в node с полным ICU, и в chromium — локаль `ru-RU` для KZT не подставляет символ тенге.
  Значит **настоящее приложение в браузере пользователя показывает «KZT» во всех 47 местах**,
  где зовётся `formatMoney` (`src/domain/statusLabels.ts:43`). Символ «₸» встречается в `src/`
  ровно дважды, и оба раза как подпись поля («Сумма, ₸»).
  **Лечение — одна строка:** `currencyDisplay: 'narrowSymbol'` в `formatMoney` даёт «216 000 ₸».
  Не применялось: `src/**` в этом заходе не трогался. **Расхождение видно на карточках:**
  превью писались с литералами «₸» (51 файл), а компоненты, которые форматируют сумму сами
  (`TransactionList`, `DealBalance`, `FurnitureMakerDashboardSummary`), печатают «KZT». Если
  чинить `formatMoney` — литералы в превью станут согласованы автоматически, переписывать их
  не придётся.
- **Компоненты, читающие данные из `DemoProvider`, показывают его СТАРТОВОЕ состояние.**
  `PayoutRequisitesForm` инициализирует поля из контекста, а `DemoProvider` стартует с
  `payoutRequisites: null` — заполненного вида в карточке не получить, сколько ни передавай
  фикстуру. То же у `RevisionRequestForm` (выбранные поля живут в `useState`, наружу пропа нет).
  Лечится засевом состояния в `PreviewShell`, но это трогает ВСЕ превью разом и сбрасывает
  уже проставленные оценки — сознательно не делалось. Если браться, то отдельным заходом
  и с полным переснятием.
- **Наблюдения по самой ДС, замеченные при написании превью** (кандидаты на доработку, не баги
  синхронизации):
  - `RevisionDiffList` печатает суммы сырыми (`1200000`, а не `1 200 000 ₸`);
  - `peer-disabled:*` в `labelVariants` мертвы, потому что в формах проекта `Label` всегда
    стоит ДО поля, а не после peer-элемента;
  - `MessageThread` визуально не различает отправителей: все реплики — одинаковая рамка,
    роль несёт только жирная подпись. Ни сторон, ни цвета, ни группировки подряд идущих
    сообщений одного автора;
  - триггеры диалогов не принимают `className` и не имеют `w-fit` — в grid растягиваются
    на всю ячейку;
  - `SelectItem.textValue` не влияет на текст в триггере (только клавиатурный поиск);
  - три находки по денежной логике вынесены отдельной задачей: замороженные спором деньги
    считаются доступными (`calculateAvailableBalance` не смотрит на статус), `dispute_open`
    отсутствует в `progressStages.ts`, комиссия 10% нигде не показана числом.
- **Брейкпоинты в карточке считаются по вьюпорту харнесса, а не по ширине ячейки.**
  `package-capture.mjs` снимает каждую историю full-bleed на 900×700. Отсюда два следствия,
  на которые уже наступали: `sm:` (640) и `md:` (768) активны ВСЕГДА, `lg:` (1024) — никогда.
  Конкретный укус: `AlertDialogFooter`/`DialogFooter` несут в базе `sm:flex-row sm:justify-end`,
  а tailwind-merge гасит конфликт только внутри одной группы модификаторов — переданный
  `flex-col` вытесняет базовый `flex-col-reverse`, но `sm:flex-row` остаётся. Все «стековые»
  варианты молча возвращались в строку и не отличались от дефолтных. Рецепт: писать
  `sm:flex-col sm:items-stretch` явно. Обратная сторона: `cfg.overrides.Sidebar.viewport`
  НЕ нужен — `md:`-сайдбар и так виден.
- **Ширина под кнопки в диалоге:** `AlertDialogContent` даёт 448 − 48 = 400px. Две длинные
  русские подписи в строку туда не влезают и уезжают за правый край карточки — штатный ответ
  дизайн-системы (и заодно честная точка оси вариантов) это колонка, а не уменьшение шрифта.
- **`btoa` в фикстурах — грабля, на которую уже наступили.** `attachmentDataUrl` собирался
  через `btoa()`, а в подписи SVG кириллица: `btoa` принимает только Latin1 и бросает
  `InvalidCharacterError`. Вычисление на верхнем уровне модуля, поэтому падала загрузка
  ВСЕГО файла фикстур — то есть каждое превью, которое их импортирует, независимо от того,
  трогает ли оно `attachmentDataUrl`. Кодируем через `encodeURIComponent`. Мораль общая:
  в `fixtures.ts` не должно быть вычислений на верхнем уровне, способных бросить.
- **Tailwind — главная ловушка этого репо.** Стили компонентов — утилитарные классы,
  компилируемые при сборке. Классов для разметки, которой нет в `src/`, в статически
  собранном CSS не существует, и они молча не работают. Поэтому
  `.design-sync/tailwind.ds.config.js` держит:
  - `content` с `./.design-sync/previews/**/*.tsx` — классы авторских превью;
  - широкий `safelist` (семейства раскладки/отступов/размеров/типографики/границ +
    семантическая палитра с альфа-шагами) — для разметки, которую пишет дизайн-агент.
  Итог ≈ 291 КБ / 2520 правил. **Перечень семейств продублирован в conventions.md — при
  правке safelist правьте и его**, иначе агент будет знать не то, что реально загружено.
  Пересборка CSS сидит внутри `buildCmd`, а не отдельной командой, именно чтобы её нельзя
  было забыть.

## Группировка карточек

Все 77 компонентов иначе падают в одну группу `general` — плоский список, в котором
невозможно искать. Группа берётся из `category` во фронтматтере документа компонента,
а настоящих документов в репозитории нет.

Решение: `.design-sync/docs/<Name>.md` — 77 заглушек, каждая содержит **только**
фронтматтер (`---\ncategory: <Группа>\n---`), плюс `cfg.docsDir: ".design-sync/docs"`.
Связывание идёт автоматически по имени файла, поэтому `cfg.docsMap` не нужен и его
не следует заводить (карта, перечисляющая все компоненты, дублирует автопоиск и
протухает при каждом добавлении компонента).

**Почему заглушка не портит `.prompt.md`:** `lib/emit.mjs` уходит в ветку синтеза при
пустом теле документа (`if (c.docBody)`), а `category` парсится отдельно. То есть из
заглушки берётся только группа, а справка для дизайн-агента (интерфейс пропсов +
примеры из превью) остаётся сгенерированной. **Не дописывайте в заглушки текст**, если
не готовы писать полноценную документацию: любое непустое тело ЗАМЕНИТ синтезированный
`.prompt.md` собой.

Группы: `basics` (19), `dialogs` (17), `deal` (13), `layout` (10), `money` (9),
`order-forms` (5), `communication` (4).

**⚠️ Названия групп обязаны быть на латинице.** `package-build.mjs:778` слугифицирует
категорию как `toLowerCase().replace(/[^a-z0-9]+/g, '-')`. Кириллица целиком выпадает из
`[a-z0-9]`, строка схлопывается в пустую, и `if (g)` её отбрасывает — **молча, без единого
предупреждения**: сборка зелёная, `docs: 77/77 matched` в логе, а все компоненты остаются
в `general`. Первая версия заглушек была русской и именно так и провалилась. Проверять
глазами: после сборки `ls ds-bundle/components/` должен показывать 7 папок, а не одну.

## Чего в карточках нет и не будет без правок в `src/`

Шесть диалогов держат `open` во внутреннем `useState` без пропа наружу, поэтому их
содержимое статично недостижимо — на карточке виден только триггер:
`SignDocumentDialog`, `CancelDealDialog`, `AcquiringPaymentDialog`,
`PayoutRequisitesDialog`, `ContractPreviewDialog`, `GuaranteeCertificateDialog`.

Это не дефект превью и не повод для `needs-work` — это граница API. Самая обидная
потеря — `SignDocumentDialog`: недостижим бланк trustme.kz с текстом документа и полем
СМС-кода, то есть ровно то, ради чего компонент существует (вдобавок `TrustMeScreen`
появляется через `setTimeout` 900 мс уже после открытия, так что одного пропа `open`
мало — нужна пара `open?` + `step?`). Схожая потеря у `PaymentProcessing`: ветки
`declined` и `timeout` — два содержательных состояния ошибки денежного контура — не
видны никак.

Если понадобится: необязательные пропы-инициализаторы (`open?`, `defaultOpen?`,
`step?`, `initialOutcome?`) пригодятся и дизайн-системе, и e2e-тестам. В рамках
синхронизации `src/**` не трогался сознательно.

Ещё две ниши, недостижимые по устройству, а не по API: операторский вариант
`Sidebar`/`RoleSwitcher` (роль выводится из маршрута, а `PreviewShell` жёстко задаёт
`/furniture-maker`) и `DisputePanel` в состоянии «спора нет» (`if (deal.status !==
'dispute_open') return null` — ячейка была бы пустым прямоугольником).

## Окружение

- `npm ci` под npm 11 не выполняет postinstall (`allow-scripts`), в т.ч. у `esbuild`.
  Проверено: `esbuild.transformSync` работает и без него (бинарь приходит из
  платформенного опционального пакета `@esbuild/darwin-*`). Предупреждение можно
  игнорировать.
- playwright: chromium build **1234** уже лежал в `~/Library/Caches/ms-playwright`, его
  пинит **playwright@1.62.1** — поставлена ровно эта версия, 200 МБ качать не пришлось.
  Если кэш обновится, сверяйте `node_modules/playwright-core/browsers.json` перед установкой.
- Путь репозитория содержит пробелы и кириллицу. В скриптах — `fileURLToPath(new URL(...))`,
  а не `new URL(...).pathname`: во втором случае путь остаётся percent-encoded и `spawn`
  падает с `ENOENT`.

## Re-sync risks

- **Данные, вклеенные в фикстуры.** `.design-sync/fixtures.ts` дублирует значения из
  `src/domain/seedScenarios.ts` (суммы, имена, названия изделий). Источник изменится —
  фикстуры не узнают. Проверять при заметных изменениях демо-сценариев.
- **`DealStatus` в `dtsPropsFor`.** Дубль графа статусов. Добавили статус в
  `src/domain/types.ts` — обновите три записи вручную, автоматика опять отдаст `unknown`.
- **Доменная модель в conventions.md.** Тот же класс риска: копия `src/domain/types.ts`.
- **Safelist vs conventions.md.** Два места с одним перечнем классов.
- **Версия тулчейна.** Декларации эмитит `tsc` из `node_modules` репозитория (5.5.x),
  CSS — `tailwindcss` 3.4.x оттуда же. Мажорное обновление любого из двух может изменить
  вывод; сборка при этом останется «зелёной», а контракты поедут.
- **`ProductHeaderMocks`, `DemoBar`, `DemoModeBanner`, `ResetDemoButton`, `RoleSwitcher`** —
  это обвязка демо-прототипа, а не продуктовая дизайн-система. Синхронизируются потому, что
  лежат в `src/components`. Если пилот превратится в продукт — исключить через
  `componentSrcMap: {"<Name>": null}`.
- **Страницы и лейауты (12 компонентов) исключены** сужением `srcDir` до `src/components`.
  Решение осознанное: агент должен собирать новые экраны, а не переиспользовать готовые.
  Если понадобятся — их нельзя вернуть просто расширением `srcDir` (см. ловушку с
  `main.tsx`), нужен отдельный barrel.
